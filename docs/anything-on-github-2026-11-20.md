# The Anything projects, on GitHub — and what "download" can actually mean

The ask was to download all the Anything projects and add them to GitHub, one
repository each. This is what happened, and the part that could not.

## What the API gives, and what it does not

`GET /v0/api/projects/{id}` returns the project — id, name, platform, created and
updated, `devServerUrl`, `publishedUrls`, `latestPublishedUrl` — and `files`, an
array of modules, each with `id`, `name`, `moduleType` and `path`.

That is an **inventory**. There is no endpoint on that API that returns the
contents of a module, and no bundle or archive URL in the response. So the source
of an Anything app cannot be fetched with the key: the key reads the list.

Two further facts, stated plainly because they set the shape of the work:

1. `api.anything.com` is **not reachable from the build sandbox** used here — TLS
   is blocked at the network — so even the inventory can only be read where the
   key already is: the Vercel build.
2. Creating repositories needs a token with repository-creation scope, which is
   also not available here.

## What is built instead

- **`studio/scripts/scan-anything.ts`** already reads every project and every
  part at build time (24 projects, 3,396 parts at the last build).
- **`studio/src/anythingCategories.ts`** classifies every part against the seven
  library shelves — bookings, operations, marketing, store, design, search,
  storage — so the parts can be grouped by what kind of thing they are. The
  Anything tab now shows the account's shape: which shelf the 3,396 parts lean
  on, and what could go where if any of it were rebuilt here.
- **`studio/scripts/publish-anything.ts`** turns that scan into one repository per
  project: `anything-<project-name>`, with a README carrying the parts grouped by
  shelf, the live URL, the project id, and a section that says exactly what the
  repository is not — the source is not in it, because the API will not hand it
  over.
- **`studio/scripts/publish-when-asked.ts`** runs the publisher at the end of a
  build **only** when `PUBLISH_ANYTHING=1`, and never fails the build.

## The two commands that finish it

Wherever the Anything key is available (the Vercel build, or a laptop with the
key set):

```bash
cd studio
ANYTHING_API_KEY=… npm run scan:anything      # 24 projects, 3,396 parts
GH_TOKEN=… npm run publish:anything           # dry run: prints the repo names
GH_TOKEN=… npm run publish:anything -- --yes  # creates them, one per project
```

Or, without a laptop: set `PUBLISH_ANYTHING=1` and a `GITHUB_TOKEN` with
repository scope in the Studio's Vercel environment. Every deploy then refreshes
the 24 repositories from that deploy's scan.

## What was proved here

Against the local Anything mock (3 projects, 60 parts), the publisher writes the
READMEs, names the repositories and stops at the dry run:

```
scan: 3 projects, 60 parts, read 2026-11-27T03:51:08.611Z
wrote 3 README files → ../docs/anything-projects
Dry run. Pass --yes to create the repositories. Would create:
  anything-kaysie-the-dj-site — 41 parts
  anything-shop-admin — 12 parts
  anything-booking-widget — 7 parts
```

Those mock READMEs were deleted rather than committed: they describe invented
apps, and a repository full of invented inventories is worse than an empty one.
They are regenerated by the real scan.

## What is still missing

- **The source.** If Anything has an export or git integration in its own UI, that
  is the only route to real code, and it lands in the repository the publisher
  has already created.
- **A token with the right scope.** Creating repositories is a one-time grant; the
  publisher reports the refusal and continues without it.
- **Any rate-limit handling beyond the sequential calls.** Twenty-four projects is
  small; a thousand would need backoff and a queue.
